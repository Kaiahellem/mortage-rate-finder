# Decisions

This document lists important choices made along the way, with reasoning
and who drove the choice.

| # | Choice | Alternatives considered | Reasoning | AI or me |
|---|---|---|---|---|
| 1 | Offer source 1: Renteportalen.no's open JSON API | Finansportalen directly (requires a distribution agreement), SSB (not split by LTV, too coarse) | Only candidate that's real, openly available without login, and already split into LTV tiers | AI suggested, I approved |
| 2 | Offer source 2: mock of a single bank's rate table (`DirectBankMockSource`) | Real scraping of DNB/Nordea's pages | Scraping is fragile (JS-rendered, changes often, unclear terms), exactly the kind of access this project calls for mocking | AI suggested, I approved |
| 3 | Trust anchor: Norges Bank's key policy rate via `data.norges-bank.no` | SSB's interest rate figures | Norges Bank is the official source for the key policy rate, free, no login, directly relevant for a below-rate check | AI suggested, I approved |
| 4 | Next.js App Router + TypeScript, no Tailwind | Plain API server (Express/Fastify) | Next.js gives both an API route and an optional minimal UI in the same framework with no extra setup; Tailwind dropped since UI is low priority | AI suggested, I approved |
| 5 | Vitest as test framework | Jest | Faster, simpler TypeScript/ESM setup, a common default choice in new Next.js projects | AI suggested |
| 6 | Renteportalen's LTV tiers interpreted as non-overlapping intervals with an inclusive upper bound (0-60, 60-75, 75-85), so 60.0 % LTV lands in the 0-60 tier | Cumulative/overlapping tiers (would have given the same selection result here, since the rate is monotonic in this data, but a less precise justification) | Matches how Norwegian banks actually tier mortgage pricing: total LTV decides one tier for the whole loan | AI suggested non-overlapping tiers but without precise boundary handling; I specified that the upper bound should be inclusive |
| 7 | LTV above 85 % results in "no offer in the data" in our solution, not "above the regulatory limit" | (pure clarification, no real alternative) | Renteportalen's data only covers up to 85 %, but the lending regulation (Lovdata forskrift 2020-12-09-2648 § 7) allows amortizing loans secured on a home up to 90 % of a prudently assessed value; Finanstilsynet has corresponding guidance on loan-to-value. The lack of offers above 85 % is therefore due to the data source, not the regulation | AI incorrectly suggested that 85 % was a regulatory limit; I corrected the factual error with a source reference |
| 8 | The mock source uses a fictitious bank name ("Fiktiv Bank AS") and has "(mock)" explicitly in `sourceName`, instead of a real bank name with made-up numbers | Use a real bank name (e.g. "DNB") with synthetic numbers | Attaching fabricated numbers to a real company name can look like real data even though `isMock: true` is in the structure; this project explicitly requires that mock data be named as mock | AI decided |
| 9 | The mock source covers 85-90 % LTV in addition to 0-85 % | Only mirror Renteportalen's coverage (0-85 %) | Shows that sources can complement each other's coverage where Renteportalen lacks data (above 85 %), and gives the selection logic something to choose between in that range. The coverage isn't drawn from any real bank's actual product range | AI decided |
| 10 | Loan amount isn't used to filter or select offers, only to flag when the winner's reference amount deviates from the stated amount | Try to scale/adjust the rate by loan amount | Neither of our sources provides amount-dependent rate tiers, so a scaling would be an invented model with no basis in data. Flagging the deviation explicitly is more honest than pretending to adjust for it | AI decided |
| 11 | Reasonable margin range for the trust check: 0 to 5 percentage points above the policy rate | 0 to 3 percentage points (stricter) | The check is a garbage-catcher for obviously wrong numbers, not a judgment of how good a rate is. Real effective mortgage rates rarely exceed about 8 %, so a cap of policy rate + 5 pp mostly catches only parsing errors and the like, without flagging real, more expensive offers as false positives | I chose, with reasoning |
| 12 | The policy rate is always fetched live from Norges Bank's API on every request, never hardcoded | Hardcode today's value for simplicity | The next rate decision is on 2026-09-24; a hardcoded value would make the trust check itself stale after that meeting | I specified this (AI hadn't explicitly ruled out hardcoding) |
| 13 | "Below the policy rate" is flagged for review, doesn't reject the offer and doesn't hide it | Automatically filter out or hide offers below the policy rate | Subsidized loans (e.g. Norway's "startlån") can legitimately sit below the policy rate; hiding them would remove real information | I specified that the flag should be shown, not hidden |
| 14 | `POST /api/best-rate` continues and reports the error in `sourceErrors` if one source fails, instead of the whole request failing | Let the whole endpoint return 500 if one source is down | One slow/down source shouldn't make the service unavailable when the other source can still respond; honest reporting of which source failed is better than hiding it | AI decided |
| 15 | "No offer covers this LTV" returns HTTP 200 with `winner: null`, not 404 or 400 | 404 (not found) | This is a valid business response to a valid request (like a search with zero hits), not a request error | AI decided |
| 16 | `RateOffer.fetchedAt` is split into `sourceUpdatedAt` (the source's own "last changed" date) and `retrievedAt` (our actual fetch time) | Just rename one field | `fetchedAt` was actually wrong, not just misleadingly named: it held Renteportalen's `oppdatert` date, not the time we called the API. Without the split, a "stale" flag would be nearly meaningless since we don't cache: a field that's always "now" on every live call would never catch that the source's own figures are actually old | I found this while reviewing my own output/code, not the agent |
| 17 | The trust check now runs on all `consideredOffers`, not just the winner | Keep only checking the winner | Confirmed bug: a three-month-old mock offer wasn't flagged because it lost on price and was therefore never checked. An offer shouldn't escape a valid stale-data flag just because it didn't win | I found this while reviewing my own output, the agent confirmed and fixed it |
